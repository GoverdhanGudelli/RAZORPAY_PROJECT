Agent Status: Static

Your current build is a static, single-run script, not a persistent service. Here's precisely why:

executor_v2.py runs top-to-bottom once, reads data/transactions.csv, processes it, writes logs/*.jsonl, and exits — no server, no listener, no way to receive new failed-payment records without manually re-running from the terminal
The "dashboard" is a static HTML file baked from a JSONL snapshot at build time — it has no live connection to anything, confirmed directly by the confusion you hit earlier (stale files showing old data)
There's no database — transactions.csv and the .jsonl logs are flat files, overwritten on every run, no history retained across runs
There's no API — nothing else (a website, Razorpay webhook, or scheduler) can currently call into this agent

This is completely normal for where you are — Phase 1 was correctly scoped as "prove the decision logic and Razorpay integration work," not "build a production service." Now you're asking the right next question.

Wrap the pipeline in FastAPI — one route, POST /process-failure, accepting a single transaction JSON body (matching your TransactionFailure schema), returning the AgentAction + execution result

Database Layer — Plan

Goal: replace flat CSV/JSONL with persistent, queryable storage.

Pick SQLite to start — zero setup, file-based, upgrade path to Postgres later is a one-line connection-string change if using SQLAlchemy
Two core tables:
transactions — mirrors your TransactionFailure schema, one row per failure record, replaces transactions.csv
audit_log — mirrors your current JSONL entries, one row per decision+execution, replaces audit_log_v2.jsonl, but now append-only and permanent across runs instead of overwritten each time
Use SQLAlchemy models mirroring your existing Pydantic schemas — minimal duplication, TransactionFailure and AgentAction already define the exact shape needed
Dashboard becomes a live query, not a bake step — build_dashboard.py's job changes from "read JSONL, inject into HTML" to "query the DB, inject into HTML," fixing the staleness problem you kept hitting at its root
Suggested order

Agent Goals — Track 03: AI Revenue Recovery

Primary objective

Detect revenue at risk — classify each failed transaction (subscription, B2B invoice, one-time payment) by root cause: bank decline, insufficient funds, card expired, mandate revoked, invoice overdue, hard decline, bank downtime.
Choose the right intervention per failure type — not one-size-fits-all: silent retry, payment-link nudge, incentive offer, or human escalation.
Execute a bounded recovery workflow — real Razorpay Payment Links, gated by explicit stopping rules (max 3 attempts, 1 discount per transaction, hard-fail reasons always escalate).

Secondary objectives
4. Measure actual money recovered, not just actions taken — separate "link sent" from "payment captured."
5. Maintain a full audit trail — every decision logged with reasoning, timestamp, and outcome (success or real API error).
6. Handle real-world constraints gracefully — e.g., Razorpay's Test Mode quota — without crashing or hiding failures.
7. Stay compliant by design — no silent retries on hard declines/revoked mandates; escalation is structural, not optional.
